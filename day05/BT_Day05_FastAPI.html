1. Web Architecture là gì?

Web Architecture (kiến trúc web) mô tả cách các thành phần của một hệ thống web (client, server, database, network...) tổ chức và giao tiếp với nhau để phục vụ người dùng.

Mô hình Client – Server:

Client (trình duyệt, mobile app, Postman...) và Server (backend, API) là hai chương trình độc lập, giao tiếp với nhau qua mạng (network) bằng một giao thức chung. Client gửi request, Server xử lý và trả về response.

💡 Điểm mấu chốt: Client và Server là hai chương trình độc lập, giao tiếp với nhau qua mạng (network) bằng một giao thức chung — phổ biến nhất là HTTP.

Hình 1. Mô hình Client – Server – Database và luồng Request/Response.

Vai trò từng thành phần:

  • Client: nơi người dùng tương tác trực tiếp, hiển thị giao diện.
  • Server: xử lý logic nghiệp vụ, truy vấn dữ liệu, trả kết quả.
  • Database: lưu trữ dữ liệu (MySQL, PostgreSQL, MongoDB...).
  • Network: kênh truyền request/response giữa client và server.

HTTP (HyperText Transfer Protocol) là giao thức quy định cách Client và Server "nói chuyện" với nhau — chuẩn hóa cấu trúc của request và response.

Vòng đời một HTTP Request/Response:

REST (Representational State Transfer) là một kiểu kiến trúc (style) để thiết kế API, dựa trên nguyên tắc mọi thứ đều là tài nguyên (resource) có một URL đại diện.

Nguyên tắc thiết kế REST:

  • Client-Server tách biệt: giao diện và xử lý dữ liệu độc lập nhau.
  • Stateless: mỗi request chứa đầy đủ thông tin cần thiết, server không lưu trạng thái phiên giữa các request.
  • Resource-based: mọi thứ đều được xem là tài nguyên, có một URL đại diện. Ví dụ: /stores, /products, /orders.
  • Chuẩn hóa Method: dùng đúng HTTP Method (GET/POST/PUT/DELETE) cho từng resource.
  • Định dạng dữ liệu: thường dùng JSON.

Ví dụ thiết kế REST endpoint cho resource "product":

MethodEndpointÝ nghĩa
GET/api/v1/productsLấy danh sách sản phẩm
GET/api/v1/products/{id}Lấy chi tiết 1 sản phẩm
POST/api/v1/productsTạo sản phẩm mới
PUT/api/v1/products/{id}Cập nhật sản phẩm
DELETE/api/v1/products/{id}Xóa sản phẩm

Vì sao có /api/v1/...?

  • api: xác định đây là endpoint dành cho việc trao đổi dữ liệu (không phải trang giao diện).
  • v1: API Versioning — đánh số phiên bản để khi nâng cấp API (v2, v3...) mà không làm hỏng các client đang dùng bản cũ.

Kiến trúc phân lớp (Layered / N-tier Architecture) chia backend thành nhiều lớp, mỗi lớp một nhiệm vụ riêng, giúp dễ bảo trì và mở rộng.

Hình 3. Kiến trúc phân lớp (Layered / N-tier Architecture).

Lợi ích:

Dễ bảo trì, dễ test từng phần riêng biệt, dễ mở rộng, nhiều người có thể làm việc song song trên từng lớp.

📌 Trong dự án demo store_management, ở giai đoạn đầu ta mới chỉ triển khai lớp Presentation/API Layer (endpoints trả dữ liệu tĩnh/mẫu). Các lớp Service, Repository, Database sẽ được thêm dần ở các buổi sau.

GET /api/v1/health là một endpoint rất phổ biến trong thực tế, dùng để:

  • Kiểm tra server có đang chạy và phản hồi hay không (dùng bởi load balancer, Kubernetes, CI/CD pipeline, monitoring tool...).
  • Là endpoint đầu tiên nên xây khi bắt đầu một dự án API, để xác nhận môi trường (framework, server, cấu hình...) đã chạy đúng trước khi code các chức năng phức tạp hơn.

Response mẫu:

{ "status": "ok", "timestamp": "2026-07-27T10:00:00Z", "service": "store-management-api" }
💡 Quy tắc nhỏ nhưng quan trọng: nếu một API không trả lời được /health, coi như toàn bộ API "chết" trong mắt hệ thống giám sát — dù các endpoint khác có thể vẫn hoạt động.

  • Nêu sự khác nhau giữa GET và POST.
  • Mã trạng thái 404 và 500 khác nhau ở điểm nào? Ai gây ra lỗi trong mỗi trường hợp?
